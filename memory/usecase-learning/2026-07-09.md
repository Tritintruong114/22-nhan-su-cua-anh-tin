# Use Case Learning — 2026-07-09

## TL;DR

Hôm nay tiếp nối bài học “plain-language = trust design”, nhưng đi sâu hơn vào 2 lớp mới:

1. **Audit log phải là UI dạy người dùng tin agent**, không chỉ là log kỹ thuật. Row sự kiện nên nói rõ: agent đã làm gì, vì sao, dùng tín hiệu nào, kết quả gì, và Operating Memory bị ảnh hưởng ra sao.
2. **Settings/privacy là nơi kiểm soát agent**, nên mọi nhãn phải giúp non-tech user thấy họ đang kiểm soát nhịp theo dõi, loại trừ, thông báo, dữ liệu — không phải đang chỉnh tham số backend.
3. `usecase-factory` đang trưởng thành thành một **Decision Pack pipeline**: `00-START-HERE.md` + `01-PRODUCT-MAP.md` + `Agent-Domain-Spec.md` + prototype. Đây là format tốt cho Trí bán/build agent use case mà người không kỹ thuật vẫn đọc được trong vài phút.

## Strongest pattern learned today

**Explainability must be productized, not hidden in logs.**

Trong `ws-agent-email`, các thay đổi ở Activity Log chuyển từ ký hiệu kỹ thuật/viết tắt (`CL`, `DR`, `ND`, `Bounce`, `Memory impact`) sang row dễ hiểu:

- “Phân loại email”
- “Soạn draft” / “bản nháp”
- “Anh duyệt draft”
- “Phát hiện reply”
- “Mail bị trả lại”
- “Agent suy luận”
- “Tín hiệu phân tích”
- “Tác động Operating Memory”

Điểm quan trọng: audit log không chỉ để debug. Với agent app, nó là **màn hình niềm tin**. Người dùng cần thấy agent giống một nhân viên có thể giải trình: nó nghĩ gì, dựa trên tín hiệu nào, hành động ra sao, và học được gì từ phản hồi của mình.

## Use-case improvement notes

### Email Revenue Follow-through Agent

- **Core problem:** solopreneur/freelancer mất doanh thu vì email quan trọng không được follow-up đúng lúc hoặc bị lẫn với inbox noise.
- **Target user:** non-tech hoặc semi-tech solopreneur dùng email như pipeline bán hàng; họ không muốn học khái niệm backend như thread, NDR, correction, confidence.
- **Domain layers:** cuộc hội thoại, người gửi/khách, bản nháp, reply thật, mail bị trả lại, nhịp theo dõi, danh sách loại trừ, Operating Memory.
- **Meta layers:** approval trước khi gửi, xác nhận đóng thread, audit log giải thích được, privacy/data controls, memory có thể xem/sửa/xoá.
- **Agent decision logic:** quét email → phân loại trạng thái → ưu tiên bucket → soạn bản nháp → xin duyệt → theo dõi reply/bounce → cập nhật Operating Memory.
- **Core loop:** “Agent đã lọc nhiều email, chỉ còn vài việc anh cần quyết” vẫn là core value. Mọi màn hình nên phục vụ câu này.

Các thay đổi gần đây trong prototype tiếp tục giảm friction ngôn ngữ:

- `thread` → “cuộc hội thoại”
- `draft` → “bản nháp”
- `contact` → “người gửi” / “khách”
- `bounce/NDR` → “email/mail bị trả lại”
- `corrections` → “lịch sử sửa chữa”
- `export/download` → “tải về”
- `cadence` → “nhịp theo dõi”

Đây là hướng đúng: UI không ép user hiểu ontology của agent; UI dịch ontology đó thành trách nhiệm và quyền kiểm soát.

### Usecase Factory

`usecase-factory` đang có output contract ngày càng rõ:

- `00-START-HERE.md`: đọc đầu tiên, verdict + why + routing theo vai trò.
- `01-PRODUCT-MAP.md`: decision map cho product/non-tech stakeholder.
- `Agent-Domain-Spec.md`: cách nghiệp vụ được agent hoá trên OpenClaw.
- `screens-brief.md`: projection từ domain spec sang màn hình.
- `mockups.html` + `mockups.data.js`: prototype reviewable.
- `appendix/`: evidence, research, coverage artifact.

Bài học: với use-case pipeline cho non-tech founder, output không nên là “nhiều file nghiên cứu”. Nó phải là **Decision Pack**: người đọc biết nên Proceed/Pivot/Narrow/Kill, vì sao, và bước build tiếp theo là gì trong dưới 3 phút.

### OpenClaw-native pipeline

`run-openclaw` là hướng quan trọng: port pipeline từ Claude Desktop/slash-command sang OpenClaw runtime bằng Tavily/search, exec, sessions, file I/O. Điều này giúp Trí biến pipeline use-case thành một workflow chạy được trong chính OpenClaw, không phụ thuộc hoàn toàn vào Claude CLI.

Điểm cần giữ: output contract phải identical với Claude pipeline. Nếu runtime khác nhau nhưng artifact giống nhau, Trí có thể dùng cùng một review/playbook cho cả Claude-terminal và OpenClaw.

## Non-tech usability notes

- **Audit row phải đọc như lời giải thích của đồng nghiệp**, không như event log máy. Structure tốt: `Agent suy luận → Tín hiệu phân tích → Kết quả/state change → Tác động Operating Memory`.
- **Settings là control surface**, không phải config dump. “Nhịp theo dõi”, “Loại trừ”, “Thông báo”, “Riêng tư” dễ hiểu hơn `cadence/exclude/notification/privacy`.
- **Privacy/destructive copy phải cực rõ:** “Không thể hoàn tác” tốt hơn “Không thể undo”; “Tải file JSON: hội thoại, bộ nhớ, cài đặt” tốt hơn “Download JSON: threads, memory, settings”.
- **Emoji/icon có ích khi làm audit log dễ scan**, nhưng icon chỉ hỗ trợ. Label vẫn phải tự giải nghĩa được.
- **Non-tech user cần biết agent học gì từ họ.** “Tác động Operating Memory” nên luôn được giải thích bằng hành vi cụ thể: duyệt bản nháp, sửa câu, bác đề xuất đóng, xoá gợi ý.

## OpenClaw / Claude terminal leverage

- OpenClaw cron phù hợp với daily learning loop: đọc memory, đọc repo diff, rút pattern, ghi report — không cần mutate repo hoặc external services.
- Codex/Claude-terminal style workflow mạnh ở việc đọc repo + diff để hiểu sản phẩm đang tiến hoá theo hướng nào. Hôm nay diff cho thấy hướng: prototype kỹ thuật → prototype có ngôn ngữ người dùng và giải trình tốt hơn.
- `usecase-factory` nên giữ hai runtime: Claude Desktop cho slash-command pipeline mạnh, OpenClaw-native cho workflow trong assistant/Telegram/cron. Nhưng cả hai phải ghi cùng output shape.
- Với product repo, read-only git diff là đủ để học. Không cần push/mutate trong daily learning job.

## Reusable agent design patterns

1. **Explainable Event Row Pattern**
   - Mỗi event quan trọng của agent hiển thị: hành động, lý do, tín hiệu, kết quả, memory impact.
   - Dùng cho trust, debugging, onboarding, và training loop.

2. **Control Surface Settings Pattern**
   - Settings không chỉ là nơi đổi tham số; nó là nơi user thấy agent bị kiểm soát bởi mình.
   - Nhãn nên nói theo ý định người dùng: nhịp theo dõi, loại trừ, thông báo, dữ liệu & bảo mật.

3. **Decision Pack Pattern**
   - Use-case research output phải có entrypoint đọc nhanh (`00-START-HERE.md`) + product map + domain spec + prototype.
   - Người đọc không cần mở evidence trước để quyết định bước tiếp theo.

4. **Runtime Parity Pattern**
   - Một pipeline có thể chạy qua Claude Desktop hoặc OpenClaw-native runtime, nhưng artifact contract phải giống nhau.
   - Điều này giảm rủi ro lock-in theo tool và giúp handoff/build dễ hơn.

5. **Plain-language Gate Pattern**
   - Trước khi prototype review, quét toàn bộ label/CTA/state/audit/settings để loại backend jargon.
   - Đây là gate trust, không phải bước polish cuối.

## Risks / weak spots

- Prototype hiện đang đổi nhiều copy đúng hướng, nhưng cần tránh chỉ “dịch chữ” mà không kiểm tra flow/state reachability. Một label dễ hiểu nhưng state không reachable vẫn làm reviewer hiểu nhầm.
- Activity Log dùng icon/emoji có thể làm dễ scan, nhưng nếu quá nhiều icon hoặc thiếu hierarchy sẽ thành noise. Cần test trên màn nhỏ và người dùng thật.
- `run-openclaw` mới là port hướng dẫn/pipeline; cần kiểm thử thực tế với một use case nhỏ để xác nhận sessions/research/write/validate không vỡ trong OpenClaw runtime.
- `state.onboarding.confirmed = true` trong prototype có thể là shortcut review/demo. Nếu không ghi rõ là demo-state, reviewer có thể tưởng onboarding đã bị bypass trong product logic.

## Memory candidates

Durable enough to save:

- Explainability for agent apps should be productized as a visible trust surface, not hidden in technical logs. Audit rows should expose action, reasoning, signals, state/result, and Operating Memory impact in plain language.
- A use-case pipeline is more useful to non-tech founders when it produces a Decision Pack, not a research pile: quick verdict entrypoint, product map, domain spec, screen brief, prototype, and appendix evidence.
