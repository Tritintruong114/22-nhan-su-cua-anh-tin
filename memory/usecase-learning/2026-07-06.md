# Use Case Learning — 2026-07-06

## TL;DR

Hôm nay bài học chính không phải thêm feature mới cho Email Revenue Follow-through Agent, mà là siết chặt **agent product pipeline**: từ domain spec → screen brief → data shapes → prototype → deploy/debug. Hai điểm nổi bật:

1. Product đã đi sâu từ “màn hình” sang **state machine + object model + audit/memory loop**.
2. Prototype/debug cho thấy non-tech trust không chỉ nằm ở UX copy; nó nằm cả ở “sản phẩm nhìn có đúng/ngon không” — font, blank page, CSS bundling cũng ảnh hưởng niềm tin.
3. `to-prototype` cần được hiểu như **behavior test**: key states phải reachable bằng hành động thật, không chỉ render demo.

## Strongest pattern learned today

**Agent app đáng tin = domain state rõ + UI projection rõ + prototype reachability rõ + polish đủ sạch.**

Nếu thiếu một trong bốn tầng này:

- Có domain nhưng không có UI projection → user không hiểu agent đang làm gì.
- Có UI nhưng không có state machine → chỉ là dashboard giả.
- Có prototype nhưng state không reachable → chỉ test visuals, không test agent loop.
- Có logic nhưng deploy bị blank/font sai → non-tech user mất trust ngay trước khi hiểu giá trị.

## Use-case improvement notes

### Use case: Email Revenue Follow-through Agent

**Core problem**

Không để “tiền kẹt trong email”: lead/quote/follow-up/reply bị bỏ sót vì người bán một mình không theo dõi hết.

**Target user / non-tech usability**

Solopreneur/consultant/freelancer/agency-1-người. Họ không muốn “inbox AI” chung chung; họ muốn sáng mở ra thấy: email nào cần quyết định, vì sao, draft nào đã sẵn, có an toàn để gửi không.

**Domain layers đang rõ hơn**

- `Thread` với state machine: monitoring, awaiting_review, draft_ready, sent_pending_reply, reply_proposed_close, reply_needs_action, bounced, closed...
- `Draft` có rationale: vì sao tone/length/pattern như vậy.
- `UserVoiceProfile`, `FollowUpPlaybook`, `ContactPreference` là Operating Memory.
- `TrackedEvent` là audit trail, có `agent_thought`, `input_signals`, `state_change`, `memory_impact`.

**Meta layers mạnh**

- Trust: approval-before-send, data policy, evidence policy.
- Governance: no auto-send, no auto-close, no silent VoiceProfile changes.
- Training loop: correction/outcome → playbook/profile/rule.
- Metrics: approval rate, reply detection accuracy, follow-up coverage, corrections applied.

**Agent decision logic đã đi từ vague sang executable**

Detect → Understand → Prioritize → Dispatch/Draft → Human Decision → Track → Learn có thể map thẳng vào data/state/pseudocode. Đây là dấu hiệu use case đã qua được “chatbot idea” và bắt đầu thành product system.

## Non-tech usability notes

- **Identity Summary sau OAuth phải nói bằng ngôn ngữ business**, không phải technical scan count: “anh bán gì, khách ai, giọng viết sao, giờ làm việc thế nào”. Đây là trust bridge rất quan trọng.
- **Activity Log là màn tin cậy, không phải phụ lục kỹ thuật.** Non-tech user không cần JSON, nhưng cần thấy: agent nghĩ gì, dựa vào tín hiệu nào, kết quả ra sao, có học gì không.
- **Dashboard cần chứng minh giá trị thuê agent**, không chỉ thống kê email: threads resolved, follow-up coverage, approval rate, pipeline/deal aging.
- **Polish kỹ thuật ảnh hưởng product trust:** blank page, font serif/fallback, CSS loading sai làm user cảm giác “agent chưa đáng tin” dù logic đúng.

## OpenClaw / Claude terminal leverage

OpenClaw/Codex-style workflow có lợi thế rõ ở pipeline này:

- Đọc repo, git status, recent files, specs để giữ đúng source-of-truth.
- Chạy build/debug/deploy nhanh, kiểm tra computed style/browser khi prototype lỗi.
- Duy trì memory dài hạn về workflow mistake và design principles.
- Cron learning biến mỗi ngày làm sản phẩm thành reusable product heuristics.
- Có thể tách pipeline thành các skill: `agent-domain-spec` → `grill-to-brief` → `design-a-screen` → `brief-to-html` → `to-prototype`.

Điểm cần siết: trước khi “done”, luôn báo evidence: files changed, build status, commit/deploy info, working tree status. Hôm nay `ws-agent-email` vẫn đang ahead/modified ở prototype font fix; cần capture/commit/push khi Trí yêu cầu, không tự push trong cron.

## Reusable agent design patterns

1. **Source-of-truth ladder**
   Agent Domain Spec → screen brief/mockup → prototype → production FE. Prototype không được lấn quyền spec.

2. **Reachability gate**
   Với mỗi key state/CTA trong brief/mockup, prototype phải đánh dấu: reachable / demo-only / missing. Nếu không reachable bằng click hoặc simulated event, chưa test được core loop.

3. **Audit as product surface**
   Event log không chỉ dành cho dev. Với agent có quyết định bán hàng, audit trail là màn giúp buyer tin: agent nghĩ gì, dùng tín hiệu gì, user đã sửa gì, memory bị ảnh hưởng thế nào.

4. **Operating Memory as company asset**
   Không pitch fine-tune mơ hồ. Pitch: agent tích lũy VoiceProfile, FollowUpPlaybook, approved snippets, contact preferences, correction patterns, outcome history.

5. **Polish-as-trust rule**
   Với non-tech agent apps, lỗi font/loading/blank page không phải “frontend nhỏ”; nó là trust bug.

## Risks / weak spots

- Prototype hiện có dấu hiệu đã deploy/debug nhưng repo còn modified/ahead. Nếu không chốt commit rõ ràng, dễ mất trace “đã fix gì”.
- `screens-brief.md` có vẻ có section S2 lặp/tiến hóa từ separate S2/S3 sang master-detail; cần dọn source-of-truth khi bước tiếp theo đòi clarity.
- `handleUserDecision` pseudocode trong `data-shapes.md` có duplicate `case 'reject_close'` và một số chỗ state_change có thể ghi sai `from` nếu mutate trước khi track. Đây là prototype/spec-level issue cần sửa khi build agent layer thật.
- Chưa có explicit state-reachability matrix cho 7 màn trong prototype; đây nên là next artifact.
