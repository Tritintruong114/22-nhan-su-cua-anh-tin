# Use Case Learning — 2026-07-04

## TL;DR

Hôm nay bài học chính đến từ `ws-agent-email` và `usecase-factory`: agent app tốt không bắt đầu từ UI/prototype, mà bắt đầu từ **core responsibility loop + domain spec + trust/evidence policy**, sau đó mới chiếu xuống mockup và prototype. Với non-technical user, sản phẩm phải nói bằng “việc còn lại cần xử lý” chứ không nói bằng “AI đã phân loại inbox”.

## Strongest pattern learned today

**Responsibility Queue > Inbox Assistant.**

Một agent đáng mua phải biến dữ liệu thô thành một hàng đợi trách nhiệm nhỏ, có lý do và có kiểm soát:

- Raw inbox: “80 email mới”.
- Agent output: “80 email đã xử lý · 9 việc cần anh xử lý hôm nay”.
- Trust surface: cho user biết 71 email còn lại đã được phân loại/bỏ qua an toàn như thế nào.
- Control surface: draft + approve, không auto-send; evidence mức B mặc định, mức C khi click sâu.

Đây là khác biệt giữa chatbot/email summary và agent operating system.

## Use-case improvement notes

### Core problem

User sợ bỏ sót email gây mất tiền, mất uy tín, trễ cam kết, hoặc thiếu context cho meeting. Agent được “thuê” để bảo vệ cơ hội và trách nhiệm trong inbox, không phải để đọc hộ email cho vui.

### Target user / non-tech usability

Ngôn ngữ nên bám vào kết quả vận hành:

- “Việc cần anh xử lý hôm nay” thay vì “high priority messages”.
- “Ai đang chờ ai?” thay vì “thread classification”.
- “Vì sao nổi?” thay vì “model explanation”.
- “Xem coverage” để chứng minh phần bị bỏ qua là an toàn.

Non-tech user cần ít câu hỏi onboarding: 1 câu risk intent → connect Gmail → scan 30–90 ngày → Risk Profile Draft → confirm/correct → queue.

### Domain layers

- Lead / Opportunity: quote, proposal, payment, order.
- Sales Conversation: ask, objection, commitment, next step.
- Follow-through: waiting_on, aging, due date, cadence.
- Trust / Approval: draft approval, no auto-send, guardrails.

### Meta layers

- Risk Profile: money/reputation/meeting/relationship priority is user-specific.
- Operating Memory: approved examples, correction history, cadence, customer/domain priority, exclude rules.
- Evidence Policy: B default, C on click.
- Governance: Gmail scopes, retention, purge, audit, no shared model training.
- Training Loop: correction/outcome → rule/memory/playbook → future decision improvement.

## Non-tech usability notes

- First screen must explicitly explain permission and safety: minimal scopes, reads email to perform task, drafts require approval, no auto-send, no shared-model training, retention/purge.
- Queue should not appear before calibration. The queue is credible only after user has confirmed/corrected the Risk Profile Draft.
- UI should show agent work happened before the queue: “Phân loại → Quản lý → Điều phối”.
- Evidence should be enough to trust, not enough to feel surveilled. Pattern + masked subject snippets by default is the sweet spot.
- User needs an audit escape hatch: main surface concise, but full classification/coverage accessible.

## OpenClaw / Claude terminal leverage

OpenClaw advantage for this type of product:

- Local memory files preserve product lessons and source-of-truth decisions across sessions.
- Cron can run daily learning and turn messy product work into reusable patterns.
- Terminal/Codex/Claude-style workflows can inspect repos, compare docs/mockups/prototypes, run checks, and produce evidence before reporting done.
- HITL approvals and audit language map naturally to agent products: agent can draft/recommend, user approves risky actions.
- Browser/static prototype deployment lets non-tech users review the experience without reading specs.

Usecase-factory advantage:

- Decision Pack forces the idea through research, product map, Agent-Domain-Spec, screen brief, mockup, then prototype.
- `Agent-Domain-Spec` prevents the common mistake: jumping from core loop directly to UI.
- `to-prototype` should run only after static mock is approved; every key mockup state should be reachable through real user actions, not hidden demo toggles.

## Reusable agent design patterns

1. **Core / Domain / Meta split**
   - Core: the painful job the agent is hired for.
   - Domain layers: business objects and lifecycle.
   - Meta layers: trust, memory, approval, evidence, governance, metrics.

2. **Responsibility reduction loop**
   - Detect → Understand → Prioritize → Dispatch → Human decision → Track reply/outcome → Update Operating Memory.

3. **Evidence ladder**
   - A: pattern only — often too vague.
   - B: pattern + masked examples — default trust layer.
   - C: full thread/evidence — only on click.

4. **Training without fine-tuning**
   - Human correction/outcome becomes rules, memories, approved snippets, cadence preferences, and playbook updates.

5. **Source-of-truth discipline**
   - Mockup data/HTML first for visual state review.
   - Screen brief for requirements.
   - Prototype only after mock states are complete and confirmed.

## Risks / weak spots

- If UI says “processed 80 emails” without coverage, skeptical users won’t trust the reduction.
- If onboarding asks too many questions, it kills the agent magic. Keep it to 1–3 questions and let scan produce a draft profile.
- If evidence is too vague, trust fails; if too detailed by default, privacy discomfort rises.
- If prototype work starts before mockup/source-of-truth alignment, product review becomes noisy and expensive.
- If the agent claims “learning” as model fine-tuning, it creates unnecessary trust/legal confusion. Better: Operating Memory and playbook rules.
