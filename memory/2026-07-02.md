## Brainstorm: Agent App / Email Revenue Follow-through
- Trí is exploring Agent App / OpenClaw product positioning with a strong preference for deep product critique, not surface feature lists.
- Useful evaluation frame: `Core / Layers / Features / Unique`.
  - Core = the central job/problem the product or candidate is hired to solve.
  - Layers = meta-capabilities around the core that make it stronger.
  - Features/evidence = concrete expressions tied to layers.
  - Unique = the connected system of layers that makes the product/person hard to replace.
- For agent products, judge features by asking: does this feature belong to a clear layer, does the layer strengthen the core, and do all features connect into a system solving the core problem?
- Candidate hiring analogy:
  - Candidate Core = hard problem the person solves better than others.
  - Candidate Layers = hard skills + soft skills + domain context + execution style.
  - Candidate Features = concrete evidence.
  - Candidate Unique = these skills connect into one coherent problem-solving capacity.

## Training Loop for Agent Quality
- Missing ingredient for the agent is `Training Loop`.
- Training in V0 does not need to mean fine-tuning a model. It means: human correction -> agent extracts pattern -> stores rule/memory/playbook -> applies it to similar future emails -> measures whether approval/edit/success improves.
- Training converts how the business sells into rules, memory, policy, and examples.
- Training layers:
  - Product / offer: catalog, prices, discount policy, delivery/payment rules, FAQs, case studies -> product knowledge base, allowed claims, quote templates, guardrails.
  - Customer / segment: VIPs, industry, deal size, purchase history, communication style -> customer memory, priority/tone rules, segment playbooks.
  - Sales process: stages, stage-change conditions, follow-up rules, escalation rules -> thread state machine, next-best-action policy, lost-risk signals.
  - Communication / reply: approved drafts, edited drafts, good emails, phrase preferences -> tone profile, reply patterns, objection examples, approved snippets.
  - Decision / approval: what Trí approves, edits, rejects, or wants escalated -> approval policy, confidence thresholds, auto / needs approval / forbidden rules.
- Training moments:
  - Setup training during onboarding.
  - Correction training whenever a human edits/rejects/changes a stage.
  - Outcome training when a deal is won/lost/no-response.
  - Periodic review training weekly to summarize what the agent learned and where it is weak.
- Training features worth building:
  - Teach from correction.
  - Approved examples library.
  - Playbook editor.
  - Customer memory.
  - Outcome feedback.
  - Training review report.
- Training inputs: email threads, product/catalog/pricing, approved/rejected drafts, human edits, deal outcomes, CRM/order/payment data, explicit instructions.
- Training outputs: rules, memory, approved snippets, scoring policy, follow-up policy, approval policy, updated playbook, confidence threshold.
- Metrics:
  - Quality: approval rate, edit distance, rejection rate, lead/stage classification accuracy.
  - Revenue: hot-lead response time, follow-up coverage, deal leakage, quote-to-close rate, revenue influenced.
  - Trust: asks at the right time, over-autonomous actions, pricing/discount/policy errors, safe auto-action rate.

## Product Direction: Core Agent Operations for Gmail Follow-through
- Trí clarified the main agent business logic should be framed as `Phân loại -> Quản lý -> Điều phối`, not merely follow-up reminders or draft generation.
- Durable core sentence: Agent phân loại thread, quản lý trạng thái chờ/phản hồi, và điều phối hành động tiếp theo để người dùng không rơi mất các cuộc hội thoại đáng giá.
- Important framing: this is a `mini-pipeline operator in Gmail`, not an email reminder app.
- `Detect + Draft` are implementation/UI actions, not the product's real business logic.
- Thread classification should answer what action is needed from whom, including examples like:
  - `awaiting_their_reply` / awaiting external reply.
  - `awaiting_my_reply` / needs user reply.
  - `reply_needs_action` when a substantive reply contains a new ask.
  - substantive reply without a new ask -> suggested close.
  - out-of-office, delivery failure, declined, partial ack should not be collapsed into one generic auto-reply bucket.
  - low-value / lower-priority threads should be handled carefully and not hidden aggressively.
- Agent should keep persistent thread state, not just rescan Gmail every morning. Suggested lifecycle: `Detected -> Classified -> Waiting -> Due -> Drafted -> Approved/Sent -> Tracking -> Replied/Snoozed/Closed`.
- Per-thread metadata worth preserving in specs: `waiting_on`, `reason_summary`, `last_meaningful_message`, `suggested_follow_up_date`, `priority/risk`, `value_type`, `confidence_label`, and `next_action_hint`.
- Coordination layer should aggregate many threads into a daily action plan, e.g. ready-to-send drafts, needs human decision, safe to wait, suggested close, and lower priority.
- V0 should expose only a few user-facing buckets even if the backend state machine is richer: Ready to follow up, Needs your reply, Waiting safely, Suggested close, Lower priority.
- `low_value_thread` is risky because hiding a real lead damages trust; default should be conservative. Prefer wording like `Lower priority` or `Maybe skip`, collapsed or placed low in the digest, not treated as permanently unimportant.
- `Needs your reply` should likely exist in V0 because follow-through includes situations where the other party replied and now the user is the blocker.
- Success metrics proposed for this wedge: saved follow-ups per week, approval rate of suggested drafts, and wrong-surface rate.

## Operating Memory vs Training Language
- Avoid calling the meta-core `training loop` or `đào tạo agent` in user-facing material because the product promises not to train/fine-tune on user email.
- Use safer framing: `Operating Memory Loop`, `Preference Loop`, `Voice Profile`, `Follow-up Playbook`, `Personalization Rules`.
- Correct privacy wording: Agent may read email to perform the user’s workspace task, classify threads, and personalize drafts, but it does not use email to train/fine-tune a shared model.
- Operating Memory should be framed as private/user-specific preferences and rules extracted from behavior such as approve/edit/reject/dismiss/snooze/close.
- Learning outputs: UserVoiceProfile for tone and style, FollowUpPlaybook for rules and patterns.
- Hard boundary: operating memory can update rules/templates/preferences, but it must never expand autonomy or change an action from approval-required to automatic without explicit human confirmation.
- Useful flow: `User approves/edits/rejects -> Extract preference -> Update Voice Profile / Follow-up Rules -> Apply to next draft -> Measure approval/edit rate`.

## Day-in-the-Life Mapping: Busy Gmail Follow-through User
- Trí liked the day-in-the-life framing for the Gmail follow-through agent and asked to remember this mapping.
- Core user image: the buyer is extremely busy and does not live in Gmail. Gmail is where deals, clients, appointments, proposals, invoices, and open conversations get scattered.
- The user does not hire the agent merely to write email. They hire it so they do not have to keep the state of 30 open conversations in their head.
- Morning value moment:
  - Instead of opening Gmail and seeing dozens of raw emails, the user opens the agent and sees an action plan.
  - The plan answers: who needs my reply, who needs a follow-up, what can safely wait, what bounced, what can be closed, and what can be deprioritized.
  - Example morning digest: bounced emails to fix/resend, threads needing user reply, replies that can be closed, follow-ups due today with drafts ready, and “Có thể bỏ qua” items collapsed below.
- Morning workflow:
  - User handles high-risk/user-blocking items first, especially `Cần bạn trả lời`.
  - Agent explains why each item matters, e.g. a client asks for price confirmation before Friday, or a reply includes a new request for an updated proposal.
  - User edits lightly or approves drafts instead of writing from a blank compose screen.
- Follow-up workflow:
  - Agent surfaces threads worth nudging, such as a proposal sent 5 days ago with no reply.
  - Agent distinguishes safe waits such as OOO until a date, and repeated nudges that should become soft-close suggestions.
  - User actions should feel like approve, edit, snooze, or close rather than manually remembering every thread.
- During the day:
  - Agent quietly manages state while the user is in meetings or doing client work.
  - It tracks substantive replies vs auto-replies, bounces, sent follow-ups, suggested closes, and next reminder dates.
  - It should not spam notifications; it should only surface changes requiring action.
- Afternoon/mini digest:
  - If important changes happen, agent summarizes deltas instead of forcing the user to reread the inbox.
  - Example: “3 changes since morning: 1 client reply needs your decision, 1 email bounced, 1 thread can be closed.”
- End-of-day operating memory:
  - From user behavior such as draft edits, approvals, dismissals, and snoozes, agent updates user-specific preferences.
  - Examples: user prefers shorter follow-ups, dislikes overly salesy wording, does not want to nudge too aggressively, treats FYI threads as lower priority, or prioritizes a specific client.
  - Keep privacy wording clear: this is private operating memory/preferences, not training/fine-tuning a shared model on user email.
- Product feel to preserve:
  - “Mỗi sáng, agent biến inbox lộn xộn thành một danh sách việc cần xử lý: ai cần mình trả lời, ai cần mình nhắc, cái gì nên chờ, cái gì có thể bỏ qua.”
  - This is the practical value for a busy user: turn inbox chaos into a coordinated action plan.

## Inbox-to-Responsibility Framing: 80 Emails -> 9 Decisions
- Trí liked the framing that the agent should not headline raw inbox volume as the main user burden.
- Avoid making the primary headline sound like `Hôm nay có 80 email`, because that pulls the user back into inbox mindset.
- Preferred product framing: `Hôm nay em đã xử lý 80 email mới cho anh. Chỉ có 9 việc cần anh nhìn.`
- Core mental model: user should not see `80 emails to read`; they should feel `80 emails were filtered by the agent, leaving only the decisions that deserve my attention`.
- Example breakdown to preserve:
  - `Bounced`: 1 email needs address fix so the pipeline can continue.
  - `Cần bạn trả lời`: 3 threads where clients are waiting on the user.
  - `Đã có reply`: 2 threads where agent suggests close/snooze.
  - `Cần follow-up`: 3 due threads, drafts ready or one decision needed.
  - `Có thể bỏ qua`: 71 emails deprioritized/collapsed, such as newsletters, FYI, auto-acks, and low-priority threads.
- Strong product line: `Không phải “anh có 80 email”. Mà là “em đã đọc 80 email, chỉ còn 9 quyết định đáng làm phiền anh”.`
- Product distinction: the app does not show the inbox; it shows the remaining responsibility of the user.

## Thinking Pattern: Transform Raw Inputs Into User Responsibility
- Trí clarified he wants to preserve the thinking pattern, not just the copy line.
- For this Gmail agent concept, do not think in terms of raw inbox objects (`80 emails`, `unread count`, `threads scanned`) as the user-facing value.
- Think in terms of transformation: raw inbox volume -> agent classification/coordination -> remaining human responsibility.
- Good product reasoning pattern:
  1. Start with the user's anxiety or repeated behavior, e.g. checking Gmail every 5 minutes to reassure themselves they are not missing anything.
  2. Identify the raw chaos the user sees, e.g. 80 emails, mixed clients/newsletters/invoices/auto-replies.
  3. Ask what the agent already absorbed/handled before bothering the user.
  4. Collapse raw volume into a small number of decisions the user must make.
  5. Phrase the output as relief and control, not as another inbox count.
- Product frame to reuse: `The app should not show the inbox; it should show the remaining responsibility of the user.`
- Copy should imply agency and filtering: `Em đã đọc/sort/triage X emails; chỉ còn Y việc đáng làm phiền anh.`
- Avoid UI/copy that re-centers the user's attention on email volume, because that recreates the anxiety the agent is meant to remove.
- Always evaluate agent UX by asking: does this screen reduce the user's need to self-check, self-triage, and self-reassure?
